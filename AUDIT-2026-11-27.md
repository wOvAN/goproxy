# Audit: goproxy (goproxy.io)

**What this repo does:** A Go module proxy. It answers the Go module proxy HTTP protocol (`/p/<mod>/@v/...`, `/sumdb/...`). In direct mode it shells out to the local `go` command and serves files from the on-disk download cache; in router mode it fetches from an upstream proxy chain, caches, and serves. There is no database and no auth.
**Load assumed:** a public or company-wide proxy: many concurrent `go` clients hitting a hot file cache, plus one background GC goroutine, plus outbound HTTP and `go` subprocesses. Judged against that.

I read fully: `main.go`, `proxy/server.go`, `proxy/router.go`, `proxy/chain.go`, `proxy/cachecontrol.go`, `proxy/metrics.go`, `sumdb/handler.go`, `gc.go`, `logger/logger.go`, the router tests, Makefile, CI configs, Dockerfile. Skimmed: chain/sumdb/gc/renameio tests.

Audit date: 2026-11-27, commit `aaa8dc7`.

---

## Must fix

**1. Proxy password leaks to every client in a 502 body** (`proxy/router.go:682-701`)
- **What this is:** When every upstream in a `-proxy` chain fails with a network error, `serveChainFailure` answers 502 with the raw Go error text as the body.
- **Problem:** The chain URL supports `https://user:pass@corp-proxy:3128` (same as `GOPROXY`). On a DNS failure the client receives `Get "https://user:pass@corp-proxy:3128/...": dial tcp: lookup ...` - the proxy password, served unauthenticated to anyone who requests a module.
- **Fix:** Answer a fixed string ("all upstream proxies failed") and send `err` to `logger.Warn` instead of the wire. Two lines.
- **If we skip it:** Anyone can read the corporate proxy credentials by requesting any module while the upstream is down, which the same code retries and logs.

**2. The `go` subprocess is tied to no context, so one hung fetch can stall the whole proxy** (`main.go:287-298`, `main.go:336-344`)
- **What this is:** Direct fetches run `exec.Command` (no context). `ops.NewContext` throws the request context away. Concurrency of subprocesses is capped by `goCmdSem` (2*NumCPU).
- **Problem:** A `go mod download` against a black-holed host never returns. `-fetchTimeout` cancels the HTTP request, not the subprocess. The semaphore slot is never released and `doOnce` keeps merging new requests onto the stuck flight, so goroutines pile up on `fl.wg.Wait()` and after 2*NumCPU hangs every cache miss across the proxy stops. An attacker triggers this by requesting modules on hosts with dead IPs.
- **Fix:** In `goJSON`, use `exec.CommandContext` with `context.WithTimeout(context.Background(), fetchTimeout)` (background, not the client's ctx, because one run is shared by many waiters). One place, no callers change.
- **If we skip it:** One flaky git server, or a modest probe attack, takes the proxy down until restart.

**3. Every streamed 200 is counted as `status="0"` in metrics** (`proxy/metrics.go:24-45`)
- **What this is:** `metricsResponseWriter` learns the status only from `WriteHeader`.
- **Problem:** `http.ServeContent`'s plain 200 path calls `Write`, not `WriteHeader`. So the hot path - cached `.zip`/`.mod`/`.info`, every `serveFile` - is counted as `goproxy_router_request_total{status="0"}`. A dashboard alert on "non-2xx" fires on a perfectly healthy proxy; the 200 rate is invisible. The older `responseLogger` (`main.go:297-306`) defaults to 200, so the two logs disagree too.
- **Fix:** Add a `Write` method that sets `statusCode = 200` when it is still 0, in metrics.go. Three lines.
- **If we skip it:** Metrics are misleading exactly where the traffic is; capacity and incident decisions get made on "0".

## Should fix

**4. GC deletes a hot cache on `noatime` mounts** (`gc.go:21-25`, `gc.go:60-66`)
- **What this is:** `sweepCache` deletes cache files whose last-access time is older than `-gcKeep` (14 days default).
- **Problem:** On filesystems mounted `noatime` (a common tuning choice on proxy hosts) access time never updates, so atime equals creation time. The sweep then deletes the most popular `.zip` files every 14 days, and the next requests hammer upstream and the `go` command. The code comment claims the sweep is "safe to run against a live cache", which is only true when atime updates.
- **Fix:** One line in `-gcInterval` help and README: "requires atime updates; on `noatime` mounts the GC deletes hot cache files."
- **If we skip it:** Periodic cache wipes on tuned hosts, blamed on upstream, invisible in logs (the sweep logs success, not suspicion).

**5. CI cannot build this code** (`.circleci/config.yml:8,27`)
- **What this is:** Both CI jobs run `circleci/golang:1.13`.
- **Problem:** `go.mod` says `go 1.27.0`. Go 1.13 refuses to parse it, so `make tidy` fails and both jobs are red for every commit. The e2e the repo requires ("new code must pass the live e2e") has no working runner.
- **Fix:** Switch the image to a Go 1.27 image (e.g. `cimg/go:1.27`), or drop CircleCI and add the two e2e jobs to the existing GitHub Actions. Deletion preferred.
- **If we skip it:** No automated safety net; the badge in README lies.

**6. Upstream retry loop ignores client cancellation** (`proxy/router.go:566-579`)
- **What this is:** Chain steps retry transport failures with `time.Sleep(delay)`, up to two times.
- **Problem:** The request context is used for the HTTP calls, but `time.Sleep` does not listen to it. When a client disconnects (go command timeouts are short), the goroutine keeps sleeping and re-fetching a dead upstream for up to ~3 more seconds. Under a cancel storm on a dead upstream this multiplies work per real client.
- **Fix:** Replace `time.Sleep(delay)` with `select { case <-time.After(delay): case <-r.Context().Done(): return }`. Three lines.
- **If we skip it:** Dead upstream + many timeouts = a queue of zombie fetchers behind every request.

**7. `@latest` is served with two different Content-Types** (`proxy/server.go:194-195` vs `proxy/router.go:757-759`)
- **What this is:** Direct mode serves `@latest` as `application/json` (it is an info JSON file). The router cache path serves the same file as `text/plain; charset=UTF-8`, and `router_test.go:88` pins that value.
- **Problem:** The `go` command does not care, but caches, CDNs and debuggers key on Content-Type; the same URL answers differently depending on the mode. A test now locks the odd value in.
- **Fix:** Return `application/json` for `/@latest` in `contentTypeFor`, update the one test line.
- **If we skip it:** Harmless today, one confusing bug hunt later.

## Nice to have

**8. `/metrics` is served on the public listener** (`main.go:309-318`)
- **What this is:** `requestLogger` answers `/metrics` on the same port as module traffic, unauthenticated.
- **Problem:** A public proxy exposes its full traffic counters (module popularity, status mix, modes) to anyone.
- **Fix:** Bind the promhttp handler to a second `-metrics` listen address; 5 lines in `main.go`.
- **If we skip it:** Free reconnaissance; no functional harm.

**9. sumdb re-implements the Cache-Control rules by hand** (`sumdb/handler.go:286-295,269` vs `proxy/cachecontrol.go:19-35`)
- **What this is:** `respondSumdb` and `serveCache` hardcode `max-age=604800` / `max-age=60`; `cacheControlFor` in the `proxy` package computes the same rules, and the router already calls it for sumdb paths.
- **Problem:** Change `immutableExpire` once and the two copies drift; clients cache sumdb tiles for a week from a rule nobody edits together.
- **Fix:** Export `cacheControlFor` and call it from the sumdb handler; delete the literals.
- **If we skip it:** The two rule lists diverge silently.

**10. `serveFromCache` returns a value nobody reads** (`proxy/router.go:784`)
- **What this is:** It returns `(found, served bool)`.
- **Problem:** All four callers use `_, served :=` (router.go:407,423,451,683). `found` is pure plumbing.
- **Fix:** Drop the `found` return.
- **If we skip it:** Nothing; it is just 5 lines to read forever.

**11. Dead code in the public `proxy` package** (`proxy/server.go:291-292,317-330`)
- **What this is:** `memFile.Readdir` and exported `NewInfo`.
- **Problem:** The `File` interface (server.go:111-116) has no `Readdir`, and a grep over the whole tree (code, tests, docs) finds zero callers of both, only doc-comment mentions. `NewInfo` is exported API, so deleting it is an owner's call, not mine.
- **Fix:** Delete `Readdir` now; delete `NewInfo` (and its two doc mentions) if no outside consumer is known.
- **If we skip it:** 16 lines to maintain, one JSON struct that duplicates the info format in two places.

---

**Verdict:** Healthy core - path traversal, cache poisoning, negative caching, stale-on-error and the go subprocess bound are all thought through and tested; fix 1 (credential leak) and 2 (unbound `go` subprocess) before running this for real traffic, 3 and 5 right after.

**Lean:** -35 lines, -0 dependencies possible (deps are all used; the vendored renameio/robustio earn their keep).

**Not checked:** README body and docs/CLI.md prose, contrib/ and scripts/ deploy files, GitHub Actions docker.yml beyond the header, renameio/robustio internals (vendored from Go), gc_darwin/gc_windows, the live e2e (needs a running proxy and network), and no load test was run. Five smaller nits left out (GC counts bytes for files whose removal fails; `-cacheExpire` help says "(min)" for a duration flag; the 302 flow in single-upstream mode sends the final body with a 302 status; contrib stackfile uses Traefik v1 labels; `permanentTransportError`'s `strings.Contains` on error text).
